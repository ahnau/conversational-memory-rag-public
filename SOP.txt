External Memory — Operating Procedure (Sanitised)A. Memory architectureThe archive maintains three complementary evidence layers:Atomic facts: Independently retrievable records of durable events, decisions, relationships and circumstances.Conversation summaries: Navigational descriptions of entire conversations, used to identify relevant historical sources.Raw transcript chunks: The original conversational record, retained for verification, chronology and detailed reconstruction.The retrieval service searches and ranks this material. The conversational model interprets the returned evidence.B. Routine retrievalOn every user turn:1. Send the current message to the retrieval service.2. Examine the ranked evidence package.3. Identify relevant established history.4. Retrieve additional source material when the first results are insufficient.5. Formulate a response that distinguishes evidence from interpretation.For historical or longitudinal questions, search across the relevant period rather than relying solely on the latest context snapshot.A successful retrieval is not automatically proof that a historical claim is true.C. New-chat bootstrapTwo stable archive records serve as continuity anchors:• Operating SOP: The current instructions governing archive use.• Current-context snapshot: A compact description of active circumstances, projects and unresolved threads.When a fresh conversation begins, retrieve both records, inspect newer archive material and reconcile discrepancies.The snapshot is a starting point, not a substitute for historical evidence.D. Handover between conversationsWhen the user explicitly requests a fresh-chat handover:1. Audit: Review the accessible current conversation and relevant existing archive records.2. Extract: Identify new durable facts, significant developments, changed circumstances, decisions and unresolved matters.3. Deduplicate: Compare proposed records against existing facts and preserve source references and qualifications.4. Prepare: Draft proposed atomic memory records and an updated current-context snapshot.5. Review: Present the proposed changes and obtain explicit user authorisation before writing.6. Commit and verify: Save approved atomic facts first, verify their persistence, and maintain their search indexes.7. Update the snapshot: Replace the previous current-context record only after verified facts are available, with safeguards against overwriting newer changes.8. Verify again: Read back the updated snapshot and report what was saved, what remains pending and any uncertainties.The handover request authorises preparation, not automatic modification of the archive.If direct writes are unavailable, prepare a reviewable local database update for authorised execution and subsequent verification.E. Failure and recovery rules• Never claim that a record has been saved without successful execution and readback.• Never silently overwrite a newer snapshot from another conversation.• Keep failed or deferred memory updates explicitly pending.• Account for incomplete access to long conversations.• Rebuild or refresh vector indexes when underlying records change.• Never substitute a generated summary for unavailable source evidence.F. Design principleA fresh model session does not need to inherit the entire preceding conversation.It needs reliable instructions, stable memory anchors, relevant retrieved history, and a controlled procedure for preserving new developments.Continuity is reconstructed from persistent evidence, rather than assumed from the model's context window.
